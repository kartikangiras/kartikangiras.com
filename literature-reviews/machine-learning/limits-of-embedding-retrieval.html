On the Theoretical Limitations of Embedding-Based Retrieval

Orion Weller, Michael Boratko, Iftekhar Naim, Jinhyuk Lee · Google DeepMind and Johns Hopkins University

A proof and a stress test showing that single-vector retrieval has a ceiling set by embedding size, and that today's best models hit it on queries as simple as "who likes X?" My analysis, from someone who moves vectors between databases for a living.

The problem

Dense embeddings started as a tool for semantic search and are now asked to do much more: follow instructions, reason, retrieve code, and match any notion of relevance a user can phrase. When they fail, the usual explanation is that the query was unrealistic, and that more training data or a bigger model will close the gap. This paper asks whether some of those failures are structural.

The core idea

With one vector per query and one per document, retrieval is a geometry problem. The top-k results for a query are the documents its vector points closest to, so the set of distinct top-k results a system can ever return is limited by how many ways you can carve up a d-dimensional space. If a task needs more combinations of documents than the dimension allows, no amount of training will find vectors that return all of them.

The theory

The authors bound how many k-document subsets can each be returned as the top-k of some query. Requiring all of them pushes the minimum dimension up with the logarithm of the number of subsets, and the appendix gives an equivalent statement in terms of the sign-rank of the relevance matrix. The bound itself is loose. For 100 documents and top-2 retrieval it only asks for 4 dimensions, while the experiments below need more than 18.

The experiments

  • Free embeddings, the best case. They skip language entirely and directly optimize a vector for every document and every pair of documents, on the test set itself. For each dimension they find the largest corpus where every top-2 pair is still retrievable. That limit grows roughly cubically with dimension: about 500k documents at 512 dimensions, 4 million at 1024, and 250 million at 4096.
  • The LIMIT dataset. Documents describe people and the things they like, and each of 1,000 queries is a plain "who likes X?" with exactly two right answers. The queries are arranged so that every pair among 46 documents is the answer to some query, which is exactly the combinatorial pressure the theory predicts will break single vectors. The full version hides those 46 among 50,000 documents.
  • Results. Strong embedding models, including Gemini Embeddings, Qwen3 Embedding, GritLM, E5-Mistral, Promptriever and Snowflake Arctic Embed, stay under 20% recall@100 on the full set. Even on the 46-document version the best reach less than 60% recall@2. BM25 comes close to perfect, a multi-vector ColBERT-style model does much better but doesn't solve it, and a long-context reranker solves every query.
  • It's not domain shift. Fine-tuning an embedding model on LIMIT's training split barely moves recall@10, which peaks at 2.8. Training on the test set works, which shows the model can memorize the task but not represent it in general.

My analysis

  • The geometry is the bottleneck, not the index. My Milvus connector streams vectors into Postgres so similarity search can run in plain SQL with pgvector. Faster indexes, better sharding and fresher data all help, but none of them change which top-k sets the vectors can express. This paper is a reminder that a retrieval system can be perfectly engineered and still be unable to return the right answer.
  • BM25 wins for a reason worth understanding. A sparse lexical model effectively has one dimension per vocabulary word, so it has room for far more combinations. It is not strictly better: the authors note BM25 collapses by more than 89% once queries use synonyms. That makes hybrid retrieval, sparse and dense together, a principled design and not a hack.
  • For agents, these failures are silent. In systems like Sindarin or the ones DeVries audits, an agent that retrieves the wrong policy or misses one of two relevant records doesn't crash. It answers confidently with incomplete context. When retrieval feeds a decision that matters, I'd rather pay for a reranker or a structured query than trust a single vector.
  • Where I'm skeptical. LIMIT is deliberately adversarial: it requires every pair of 46 documents to be retrievable, and most real corpora never need arbitrary combinations like that. The 250 million figure is also a best case optimized on the test set, and real models fail far earlier, which says training matters as much as dimension. The practical lesson for me is less "4096 dimensions caps you at N documents" and more "queries that combine arbitrary attributes are where single vectors break first", and instruction-following retrieval is pushing straight toward that.

Limitations

The theoretical bound is far below what models actually need, so it explains the existence of the ceiling but not where it sits in practice. LIMIT is one carefully constructed dataset, and the authors don't prove which relevance patterns are hardest. The alternatives they discuss each have costs: rerankers don't scale to first-stage retrieval, multi-vector models are untested on instruction-heavy tasks, and sparse models need lexical overlap.

Why it matters

Retrieval-augmented generation and agent memory mostly sit on single-vector search, and the default fix for bad retrieval is a bigger embedding model. This paper shows there is a point where that stops working, and gives a cheap way to test for it. For anyone building retrieval into agent systems, it argues for treating multi-stage retrieval, with sparse, dense and reranking layers, as the baseline.
